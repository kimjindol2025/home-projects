프리랭(FreeLang)으로 셀프호스팅을 완수하는 것은 **'기록이 증명이다'**라는 철학을 실현하는 가장 확실한 방법입니다. 외부 의존성 없이 스스로를 컴파일하는 단계에 도달하려면, 현재 언어의 제약을 '피해가거나' 아니면 **'언어 자체를 확장'**해야 합니다.
C로 새로 작성하는 대신 프리랭을 고수하며 셀프호스팅으로 가는 3가지 전략을 제안합니다.
1. 연결 리스트(Linked List) 우회 전략 (가장 빠른 방법)
현재 프리랭 파서가 [Expr] 같은 배열 문법을 enum 안에서 인식하지 못한다면, 재귀적 구조를 사용하여 배열을 대체할 수 있습니다.
 * 변경 전 (에러 발생):
   enum Expr {
    Call(Expr, [Expr]) // [Expr]에서 파서 에러
}

 * 변경 후 (우회 성공):
   enum Expr {
    Call(Expr, ExprList)
}

enum ExprList {
    Cons(Expr, ExprList),
    Nil
}

이 방식은 프리랭의 현재 문법만으로도 Call 함수의 인자 목록을 무한히 확장할 수 있게 해줍니다. Lisp이나 Haskell 스타일의 리스트 처리 방식을 도입하는 것입니다.
2. 포인터와 i64 활용 (시스템 프로그래밍 방식)
배열 타입을 직접 쓰지 않고, 주소값(i64)을 넘긴 뒤 내부적으로 캐스팅하여 사용하는 방식입니다.
 * 핵심 아이디어:
   * 배열의 시작 주소를 i64로 저장합니다.
   * codegen_c.fl에서 C 코드를 생성할 때 해당 값을 포인터로 취급하도록 생성합니다.
 * 장점: 메모리 구조를 직접 제어할 수 있어 성능 최적화에 유리합니다.
 * 단점: 프리랭 레벨에서 타입 안정성이 떨어지며, 수동으로 메모리 크기를 관리해야 합니다.
3. '모노리스(Monolith) 빌드'로 모듈 제약 해결
import 시스템이 없다면, 컴파일 직전에 모든 .fl 파일을 하나로 합치는 Pre-processor 단계를 두면 됩니다.
 * 워크플로우:
   * cat token.fl lexer.fl parser.fl ... > stage3_all.fl
   * freelang stage3_all.fl
 * 이 방식은 초기 C 컴파일러들이 사용하던 방식과 유사하며, 복잡한 임포트 로직 없이도 대규모 프로젝트를 관리할 수 있게 해줍니다.
📍 셀프호스팅을 위한 권장 로드맵
선택지 2(C 구현) 대신 프리랭 셀프호스팅을 계속 밀고 나간다면 다음과 같은 순서를 제안합니다.
| 단계 | 작업 내용 | 목표 |
|---|---|---|
| Step A | enum 구조를 연결 리스트형으로 변경 | [Expr] 제약 탈피 |
| Step B | 모든 파일을 하나로 합쳐서 컴파일 시도 | 모듈 시스템 부재 해결 |
| Step C | Stage 1-2 결과물로 이 통합 파일을 컴파일 | 최초의 셀프호스팅 성공 |
| Step D | 셀프호스팅된 컴파일러로 [Expr] 지원 기능을 추가 | 언어 기능 확장 (Self-Upgrade) |
"기록이 증명이다 gogs" 정신으로, 현재의 언어 제약을 프리랭만의 방식으로 돌파해 보시겠습니까?
만약 **Step A(연결 리스트 구조로 재설계)**부터 시작하신다면, ast.fl을 이 방식에 맞춰 다시 정의하는 것부터 도와드릴 수 있습니다. 어떻게 진행할까요?
