선택지를 보니 드디어 FreeLang v6가 단순한 스크립트 엔진을 넘어 **'정적 타입 시스템'**이라는 거대한 산맥을 마주했군요. 님의 스타일(Zero-Dependency & Self-hosted)을 고려했을 때, 가장 탄탄한 기초를 다지면서도 가시적인 성과를 낼 수 있는 **3번(Type System Foundation)**을 먼저 제안하고 싶지만, 실전성을 생각한다면 1번이 가장 뜨거운 감자입니다.
하지만 님의 철학인 **"기록이 증명이다"**를 가장 완벽하게 투영할 수 있는 경로는 다음과 같습니다.
🚀 추천 경로: 3️⃣ → 1️⃣ (Type System Foundation)
현재 struct 문법이 추가된 상태에서 단순한 타입 체크(1번)만 도입하면, 나중에 제네릭이나 트레이트를 추가할 때 아키텍처를 통째로 갈아엎어야 할 위험이 있습니다. 따라서 3번을 통해 '타입'이라는 개념의 뿌리를 먼저 내리는 것이 장기적으로 유리합니다.
선택 3을 먼저 해야 하는 이유 (The Architect's View)
 * 확장성: 제네릭(Generic)과 인터페이스(Trait)를 고려한 타입 그래프를 먼저 설계하면, 나중에 어떤 복잡한 구조체가 들어와도 v1.elf 수준에서 완벽히 검증됩니다.
 * 정적 분석: 님이 좋아하는 red-team 명령이 "이 변수는 타입이 맞지 않음"이라고 논리적으로 지적하려면, 기반이 되는 타입 추론 엔진이 필수적입니다.
🛠️ 실행 계획 (Action Plan: Option 3)
만약 3번을 선택하신다면, Claude Code와 함께 다음 루틴을 즉시 가동합니다.
 * /refactor-first "Type Lattice 설계"
   * Int, Float, String, Struct 그리고 Unknown 타입을 포함하는 타입 계층 구조를 정의합니다.
 * PLAN.md 업데이트
   * Hindley-Milner 스타일의 타입 추론을 도입할지, 아니면 더 단순하고 명시적인 시스템을 갈지 결정합니다.
 * Core Implementation
   * FreeLang v6 컴파일러 내부에 TypeResolver 모듈을 추가합니다.
🎯 결정의 순간
"타입은 코드의 문법이 아니라, 데이터의 증명입니다."
기초를 파괴적으로 다지고 싶다면 3번, 당장 struct를 실전에서 써먹고 싶다면 1번입니다.
