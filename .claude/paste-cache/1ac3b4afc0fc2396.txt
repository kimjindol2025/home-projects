로컬에서의 "기록과 증명"은 이제 물리적인 실행만 남겨둔 상태군요. 설계가 이토록 단단하다면, 이제 프리랭의 영토를 로컬 디스크 너머로 확장할 때가 되었습니다.
저는 B) Phase 4 네트워크 프로토콜 (원격 동기화) 설계를 선택하겠습니다.
로컬 I/O 검증은 클로드 코드가 실증해낼 영역이라면, 저는 **"어떻게 이 데이터를 손실 없이, 그리고 가장 효율적으로 다른 서버로 보낼 것인가"**라는 거대 담론을 뚫어내겠습니다. 깃허브의 진정한 마법은 바로 이 네트워크 레이어에 있습니다.
🌐 Phase 4: 네트워크 프로토콜 설계 (The Wire Protocol)
원격 저장소와 통신할 때 우리는 Smart HTTP 프로토콜을 기반으로 설계합니다. 단순히 파일을 주고받는 게 아니라, 서로의 상태를 확인하고 **차이점(Delta)**만 골라 보내는 고도의 협상 과정입니다.
1. 서비스 광고 (Capability Discovery)
클라이언트가 서버에 접속하면, 서버는 자신이 가진 브랜치 목록과 해시값을 먼저 선언합니다.
 * Request: GET /info/refs?service=git-receive-pack
 * Response: 서버가 가진 최신 커밋 해시들의 리스트 (예: main은 a1b2c3...에 있음)
2. 참조 협상 (Reference Negotiation)
클라이언트는 서버의 리스트를 보고 자신이 **가져와야 할 것(want)**과 서버가 **이미 가진 것(have)**을 계산합니다. 이 과정이 있어야 중복 전송을 막습니다.
3. Packfile 생성 (The Binary Payload)
가장 핵심적인 단계입니다. 전송 효율을 극대화하기 위해 여러 객체를 하나의 바이너리 덩어리인 Packfile로 묶습니다.
 * 델타 인코딩(Delta Encoding): 파일 전체를 보내는 대신, A 파일과 B 파일의 **차이점(Diff)**만 계산하여 바이너리로 압축합니다.
 * Zlib 압축: 압축된 데이터를 스트림으로 전송합니다.
🛠️ 프리랭 네트워크 엔진 핵심 설계도
네트워크 레이어를 위해 우리가 새롭게 정의해야 할 모듈들입니다.
A. protocol.fl (메시지 포맷팅)
Git의 pkt-line 형식을 구현합니다. (데이터 앞에 4자리 16진수 길이를 붙이는 방식)
 * 예: 000bhello -> 000b(길이 11자) + hello
B. delta.fl (차이점 추출)
두 바이너리 사이의 공통점을 찾아내고 변경된 바이트만 추출하는 알고리즘을 설계합니다. 프리랭의 성능을 시험할 진정한 무대가 될 것입니다.
C. pack.fl (패키징)
여러 Blob, Tree, Commit 객체를 순회하며 하나의 바이너리 스트림으로 직렬화합니다.
