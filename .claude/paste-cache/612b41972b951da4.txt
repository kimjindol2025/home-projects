**parser.fl 이식**은 FreeLang 프로젝트에서 가장 중요한 dogfooding(자기 언어로 자기 언어를 구현) 단계예요.  
현재 TypeScript로 작성된 parser.ts를 FreeLang 자체로 옮기는 과정은 **점진적 + 안전하게** 진행하는 게 핵심입니다. 한 번에 다 옮기려다 실패하면 디버깅이 매우 힘들어지기 때문이에요.

### 전체 로드맵 개요 (추천 순서)

| 단계 | 목표 | 예상 난이도 | 기간 추정 (혼자 작업 기준) | 검증 방법 |
|------|------|-------------|-----------------------------|-----------|
| 0    | 준비 | ★☆☆☆☆ | 1–2시간 | — |
| 1    | 최소 lexer 재현 | ★★☆☆☆ | 1–3일 | 토큰 출력 일치 |
| 2    | 핵심 AST 노드 파싱 | ★★★☆☆ | 4–10일 | 간단한 프로그램 AST 비교 |
| 3    | parser.fl로 self-parse 시도 | ★★★★☆ | 7–20일 | 동일 소스 → 동일 AST |
| 4    | 차이 좁히기 & 버그 픽스 | ★★★★☆ | 2–4주 | 100% 일치 + regressions 없음 |
| 5    | TS parser 제거 & 완전 self-host | ★★★★★ | 1–3개월 | TS 없이 빌드/실행 가능 |

### 세부 단계 (실제 작업 순서 추천)

**0. 준비 단계 (꼭 먼저)**

- 기존 parser.ts 전체를 한 파일로 복사해서 `parser-old.ts`로 백업
- parser.fl을 만들 파일 하나 생성: `src/parser/parser.fl`
- **비교 도구 준비**:
  - TS parser 실행 → JSON.stringify(ast) → 파일 저장
  - FreeLang parser 실행 → 동일 입력에 대해 ast 출력 → 비교 (diff)
- 간단한 "golden" 테스트 파일 5~10개 준비 (변수 선언, fn, if, for, import, lambda 등)

**1. 최소 viable lexer 먼저 옮기기 (가장 중요 – 기반)**

목표: 기존 lexer와 똑같이 토큰 배열을 뱉는 parser.fl 버전 만들기

- TokenType enum → FreeLang에서 const나 map으로 재현
- 주요 토큰 종류만 먼저 구현 (IDENT, NUMBER, STRING, KEYWORD(fn, if, let, import 등), OPERATOR, PUNCT)
- `advance()`, `peek()`, `consume()` 같은 기본 메서드
- `skipWhitespace()`, `readIdentifier()`, `readNumber()`, `readString()` 등 핵심 함수

검증 예시 코드 (parser.fl 안에):

```fl
fn test_lexer_simple() {
  let src = 'let x = 42 + foo();'
  let tokens = lex(src)
  println(str(tokens.length))          # 기대: 10개 정도
  println(tokens[0].type)              # "let"
  println(tokens[4].value)             # "42"
}
```

**2. Parser 기본 구조 옮기기**

- Parser 클래스 → FreeLang struct나 그냥 global 함수들로
- `parseExpression()`, `parseStatement()`, `parseBlockStatement()` 등 큰 함수부터
- precedence climbing이나 recursive descent 로직 그대로 따라 옮김 (TS 코드 보면서 copy-paste 수준으로)

우선 순위 높은 파싱 대상 (이 순서대로 구현):

1. literal (number, string, bool, null, array, map literal)
2. identifier + simple call (foo(), obj.field)
3. binary expr (+ - * / == != < > 등)
4. variable decl (let x = ..., const y = ...)
5. fn decl + lambda
6. if / else
7. for-in / for-of / while
8. import 문 (기본 + from + default import)
9. return, break, continue

**3. AST 노드 정의 옮기기**

FreeLang에 맞는 AST 표현법 결정 (가장 중요한 설계 포인트)

옵션 3가지 (추천 순):

| 방식 | 장점 | 단점 | 추천도 |
|------|------|------|--------|
| Map 기반 (key=type, value=children) | 유연, 쉽다 | 느리고 메모리 많이 먹음 | ★★★★☆ (초기 추천) |
| struct + variant-like (type tag + union) | 타입 안전, 빠름 | FreeLang에 union 없어서 번거로움 | ★★★☆☆ |
| 문자열 태그 + 배열 children | 간단 | 덜 구조적 | ★★☆☆☆ |

예시 (Map 방식 – 가장 빨리 시작 가능):

```fl
fn make_ast_node(type, props) {
  let node = map_new()
  node["type"] = type
  # props를 node에 merge
  return node
}

let expr = make_ast_node("binary", {left: lhs, op: "+", right: rhs})
```

**4. Self-parse 루프 만들기 (진짜 bootstrapping 시작)**

```fl
# minimal-self-parse.fl
fn main() {
  let src = read_file("parser.fl")   # 또는 문자열로 직접
  let ast_ts = parse_with_ts(src)     # 기존 TS parser 호출 (임시 브릿지)
  let ast_fl = parse(src)             # 새 parser.fl 호출

  if ast_equal(ast_ts, ast_fl) {
    println("Self-parse 성공! AST 동일")
  } else {
    println("차이 발견 → 디버깅 시작")
    diff_ast(ast_ts, ast_fl)
  }
}
```

**5. 점진적 확장 & 안전장치**

- 한 기능씩 추가할 때마다 **regression suite** 돌리기
- `parse_and_print(src)` 함수 만들어서 디버깅 편하게
- 에러 위치(line, column) 정확히 유지 (기존 parser처럼)
- ambiguous grammar 있으면 precedence table 조정

- Day 5–6: let, fn, if 파싱
