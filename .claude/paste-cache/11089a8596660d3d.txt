❯ 궁금한건 러스트 ts독립 못하는 이유는???

● 좋은 질문입니다. 현재 freelang-runtime이 Rust,
  freelang-v4-jit이 TypeScript인데, 이 둘이 서로
  독립적으로 실행되지 못하는 이유를 설명합니다.

  ---
  왜 Rust ↔ TypeScript가 독립적이지 못한가?

  1. 실행 환경 분리 문제

  Rust 코드                    TypeScript 코드
  ────────────                 ───────────────
  네이티브 바이너리             Node.js/Bun 런타임
  필요
  cargo build → .so/.a         tsc → .js → V8 엔진

  서로가 상대방을 직접 호출 불가

  - Rust가 컴파일한 바이너리는 TypeScript를 직접 호출
  못함
  - TypeScript는 Rust의 struct, enum을 직접 임포트
  못함

  ---
  2. 타입 시스템 불일치

  현재 EscapeIr가 두 곳에 따로 정의됨:

  // escape_analysis.rs
  pub enum EscapeIr {
      Assign { var: String },
      Return { var: String },
      ...
  }

  // escape-analysis.ts
  export type EscapeIr =
    | { op: "assign"; var: string }
    | { op: "return"; var: string }
    ...

  동기화가 깨지면 조용히 버그 발생.

  ---
  3. JIT VM 연결 끊김

  jit-vm.ts의 실행 흐름:

  [FreeLang 소스]
       ↓
  [Lexer/Parser/Compiler]  ← TS 구현
       ↓
  [VM 실행]                ← TS 구현
       ↓
  [HotspotDetector]        ← TS 구현
       ↓
  [EscapeAnalyzer]         ← TS 구현 (방금 추가)
       ↓
  [NativeCodeGen → LLVM IR] ← TS 구현 (시뮬레이션)

  [GC / Allocator]         ← Rust 구현
  [Escape Analysis]        ← Rust 구현 (방금 추가)

  이 두 파이프라인이 완전히 분리되어 있음.
  Rust GC가 TypeScript JIT의 결정을 반영 못함.

  ---
  4. 가능한 연결 방법 (현재 미구현)

  ┌─────────────┬────────────────────┬────────────┐
  │    방법     │        설명        │   난이도   │
  ├─────────────┼────────────────────┼────────────┤
  │ FFI (N-API) │ Rust → .node 파일  │ 높음       │
  │             │ → require()        │            │
  ├─────────────┼────────────────────┼────────────┤
  │ WebAssembly │ Rust → .wasm →     │ 중간       │
  │             │ TS에서 import      │            │
  ├─────────────┼────────────────────┼────────────┤
  │ gRPC/IPC    │ 소켓으로 통신      │ 중간       │
  ├─────────────┼────────────────────┼────────────┤
  │ JSON 파일   │ 분석 결과를 파일로 │ 낮음 (성능 │
  │             │  교환              │  포기)     │
  └─────────────┴────────────────────┴────────────┘

  ---
  결론

  현재 FreeLang의 구조상 Rust 런타임과 TS JIT는 설계상
   분리된 두 개의 독립 모듈입니다. 실제 통합하려면
  WebAssembly (Rust → wasm → TS import) 또는 N-API
  (Rust → .node 네이티브 모듈) 중 하나를 선택해야
  합니다.

  어떤 방향으로 통합하고 싶으신가요?

❯ 프리랭으로  끝나는 방법은.

● FreeLang으로 끝내는 방법 — 즉 FreeLang 자체가
  FreeLang을 컴파일하는 구조입니다.

  ---
  최종 목표: Self-Hosting

  FreeLang 소스 (.fl)
          ↓
    FreeLang 컴파일러 (.fl로 작성)
          ↓
    네이티브 바이너리

  Rust도 TS도 필요 없음. FreeLang이 FreeLang을 처리.

  ---
  현재 문제 (왜 아직 못 하는가)

  현재 상태:

  FreeLang 소스
       ↓
    Go/TS/Rust 로 만든 컴파일러
       ↓
    결과물

  → 컴파일러 자체가 FreeLang이 아님

  ---
  Self-Hosting 달성 단계

  Stage 0 — 지금 (Bootstrap)

  Go/TS 컴파일러가 FreeLang을 컴파일
  → 이미 어느 정도 있음

  Stage 1 — FreeLang으로 컴파일러 작성

  FreeLang으로 Lexer 작성
  FreeLang으로 Parser 작성
  FreeLang으로 Codegen 작성
  → compiler_v1.fl

  Stage 2 — Bootstrap 컷

  Go 컴파일러로 compiler_v1.fl 컴파일
  → compiler_v1 바이너리 생성

  compiler_v1으로 compiler_v1.fl 다시 컴파일
  → 결과가 동일하면 Self-Hosting 성공

  Stage 3 — Go/TS/Rust 전부 제거

  FreeLang 컴파일러만 남음
  GC도 FreeLang으로
  JIT도 FreeLang으로
  Escape Analysis도 FreeLang으로

  ---
  핵심 조건 (Self-Hosting이 되려면)

  ┌─────────────────────────┬──────────────┐
  │        필요 기능        │  현재 상태   │
  ├─────────────────────────┼──────────────┤
  │ 파일 I/O                │ ❓ 확인 필요 │
  ├─────────────────────────┼──────────────┤
  │ 포인터/메모리 직접 제어 │ ❓           │
  ├─────────────────────────┼──────────────┤
  │ 함수 포인터 / 고차함수  │ ❓           │
  ├─────────────────────────┼──────────────┤
  │ 문자열 처리             │ ❓           │
  ├─────────────────────────┼──────────────┤
  │ 재귀                    │ ❓           │
  └─────────────────────────┴──────────────┘

  FreeLang이 이 기능들을 갖춰야 컴파일러를
  FreeLang으로 작성 가능합니다.

  ---
  질문

  현재 FreeLang에서:
  1. 파일 읽기/쓰기 가능한가요?
  2. 포인터나 raw 메모리 접근 있나요?
  3. 컴파일 타겟이 뭔가요? (네이티브? WASM? LLVM IR?)

  이걸 알면 Self-Hosting 로드맵을 정확하게 짤 수
  있습니다.
