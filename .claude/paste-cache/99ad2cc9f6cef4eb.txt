셀프호스팅 관점에서 우선순위

컴파일러가 자기 자신을 컴파일하려면:

필요한 것              어떤 기능으로?
──────────────────────────────────────
소스 파일 읽기    →   파일 I/O     ← 하드 블로커
토큰 처리        →   ✅ 완료
AST 노드 표현    →   클래스       ← 소프트 블로커
IR 생성          →   클래스       ← 소프트 블로커
에러 처리        →   try/except   ← 있으면 좋음

❌ Option 1 (try/except 완성) 비추천 이유

try/except 완전 구현에 필요한 것:

1. 오프셋 패칭
   IR 생성 중에 아직 모르는 주소를 나중에 채움
   → 백패치 시스템 필요

2. 예외 테이블
   IRProgram에 handler 메타데이터 구조 추가
   → 아키텍처 변경 필요

3. 스택 언와인딩
   예외 발생 시 콜스택 역으로 풀기
   → VM 핵심 로직 변경

비용: 2-3시간
셀프호스팅 기여: 낮음 (KeyError는 이미 감지됨)

✅ 추천 순서

3️⃣  파일 I/O  →  2️⃣  클래스  →  1️⃣  try/except

이유:

파일 I/O (1-2시간)
  ├─ 구현 난이도: 쉬움
  ├─ open(), read(), write() → Node.js fs 모듈 래핑
  └─ 셀프호스팅 하드 블로커 제거

클래스 (3-5시간)
  ├─ 구현 난이도: 중간
  ├─ AST 노드를 클래스로 표현 가능
  └─ 컴파일러 소스 작성의 기반

try/except (2-3시간)
  ├─ 지금 기본 감지는 됨
  └─ 나중에 구현해도 셀프호스팅 가능

🔍 파일 I/O가 왜 먼저인가

셀프호스팅 컴파일러의 main.pf 예시
이게 안 되면 셀프호스팅 시작도 못 함

source = open("input.pf").read()   ← 파일 I/O 없이 불가
tokens = lexer.tokenize(source)
ast    = parser.parse(tokens)
ir     = compiler.compile(ast)
vm.execute(ir)

🛠️ 파일 I/O 구현 방법 (빠른 경로)

// src/stdlib/builtins.ts 에 추가
// Node.js fs 모듈 래핑이라 간단

'open': (filename: string, mode = 'r') => {
    return {
        read: () => fs.readFileSync(filename, 'utf8'),
        write: (data: string) => fs.writeFileSync(filename, data),
        close: () => {}
    }
},
'read_file': (filename: string) => {
    return fs.readFileSync(filename, 'utf8')
},
'write_file': (filename: string, data: string) => {
    fs.writeFileSync(filename, data)
}
